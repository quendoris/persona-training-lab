# Event, Error and Diagnostic Evidence Reference

> **Scope:** current v1.0 event-log, application-error reporter, rotating-log and Operations Center evidence contract.
>
> This document describes what PTL records and how those records are surfaced. It does **not** claim that diagnostic data is automatically safe to publish or that the event log is a lossless audit trail.

## 1. Evidence surfaces

PTL currently has several related but non-identical diagnostic surfaces:

```text
application/service failure
        ↓
ApplicationErrorReporter
        ├─ rotating text log
        │    <workspace>/logs/persona_training_lab.log
        │
        └─ SQLite event_log
              ↓
        OperationsCenterService
              ├─ recent activity
              └─ issue items

runtime long-running work
        ↓
runtime_operations + runtime_operation_resources
        ↓
OperationsCenterService
        ├─ active items
        └─ recent activity
```

The rotating file log and SQLite event log have different retention/deduplication behavior. Runtime operations are a separate persistent state machine, not event-log rows.

## 2. `EventRecord`

Application event storage uses the immutable record shape:

```text
id
event_type
entity_kind
entity_id
payload_json
occurred_at
correlation_id? 
causation_id?
```

SQLite columns are defined in `reference/persistence-schema.md`.

### 2.1 Event identifiers

Reporter-generated events use:

```text
evt_<12 lowercase hex>
```

Application errors use an independent incident identifier:

```text
err_<12 lowercase hex>
```

Correlation identifiers generated by the reporter use:

```text
corr_<12 lowercase hex>
```

These identifiers have different semantics and must not be treated as interchangeable aliases.

## 3. Reporter-generated event types

`ApplicationErrorReporter` currently persists two event families:

```text
application.error
application.notice
```

Other subsystems, especially Automation, may append their own event types through the event-log port. This reference section describes the reporter-generated schema only.

## 4. `application.error` payload

`capture(...)` constructs a payload with the following fields:

| Field | Current meaning |
|---|---|
| `error_id` | `err_<12 hex>` incident identity |
| `correlation_id` | supplied correlation or generated `corr_<12 hex>` |
| `component` | caller-provided component identity |
| `operation_id` | related runtime operation ID or empty string |
| `exception_type` | Python exception class name |
| `exception_message` | `str(error)` |
| `traceback` | formatted traceback, retaining at most the final 12,000 characters |
| `context` | recursively processed structured caller context |
| `user_message` | semantic UI message payload `{key, values}` |
| `fingerprint` | SHA-256 duplicate-suppression fingerprint |

The event row itself receives:

```text
event_type     = application.error
entity_kind    = caller value or application
entity_id      = caller entity_id, else operation_id, else global
correlation_id = payload correlation_id
causation_id   = NULL
occurred_at    = current UTC ISO timestamp
```

### 4.1 Error fingerprint

The duplicate fingerprint is:

```text
SHA256(component | exception type | exception string)
```

It is an incident-grouping heuristic, not a cryptographic identity of the complete traceback/context/environment.

Two errors with the same component/type/message can share a fingerprint even when their deeper context differs.

## 5. `application.notice` payload

`report_message(...)` builds:

| Field | Current meaning |
|---|---|
| `correlation_id` | supplied correlation or generated `corr_<12 hex>` |
| `component` | caller-provided component |
| `operation_id` | related runtime operation ID or empty string |
| `level` | upper-case caller level |
| `message` | caller-provided machine/diagnostic message |
| `context` | recursively processed structured context |
| `fingerprint` | SHA-256 duplicate-suppression fingerprint |
| `user_message` | optional semantic `{key, values}` payload |

Fingerprint:

```text
SHA256(component | level | message)
```

The event row uses:

```text
event_type = application.notice
```

with the same entity/correlation fallback rules as `application.error`.

## 6. Structured-context redaction

Reporter context and `UserMessage.values` pass through the recursive safe-value processor.

A mapping key is replaced with:

```text
<redacted>
```

when its case-folded spelling contains any current sensitive token:

```text
password
secret
token
api_key
key_material
authorization
cookie
credential
private_key
access_key
```

The recursion also:

- processes nested mappings;
- processes list/tuple/set/frozenset values into JSON-friendly lists;
- emits `<cycle>` for recursive container identity;
- emits `<truncated>` at depth 8;
- falls back to `repr(...)` only when ordinary JSON/default-string serialization itself fails.

### Critical privacy boundary

This is **key-based structured-context redaction**.

It does not scan arbitrary strings for secrets.

In particular, the following error fields are not passed through the context-key redactor:

```text
exception_message
traceback
```

and a non-sensitive context key can still contain sensitive text in its value.

Therefore diagnostic logs/events must be reviewed before publication or external sharing.

## 7. Rotating application log

`configure_logging(<workspace>/logs)` configures the Python root logger with:

```text
root level: INFO
console level: CRITICAL
file level: INFO
```

File:

```text
<workspace>/logs/persona_training_lab.log
```

Rotation contract:

```text
maxBytes    = 5,000,000
backupCount = 5
encoding    = UTF-8
```

Format:

```text
timestamp | LEVEL | logger-name | message
```

Recoverable service/UI errors therefore normally go to file/event evidence rather than flooding the terminal. The console is reserved for `CRITICAL`-level output from this managed logging configuration.

Failure to create the log directory/file is best-effort swallowed and must not prevent application startup.

## 8. File log versus SQLite event log

Every reporter call attempts to write the rotating file log first.

SQLite persistence is additionally subject to duplicate-window suppression.

Therefore:

```text
same repeating incident
        ↓
file log: may contain every reporter call
SQLite event_log: at most one reporter record per duplicate window
```

This is intentional flood control, not evidence equivalence.

## 9. Duplicate-window semantics

Default duplicate window:

```text
5.0 seconds
```

The reporter stores the last-seen monotonic time for each fingerprint in process memory.

A record is persisted when:

```text
fingerprint never seen in this reporter instance
OR
now - previous_seen >= duplicate_window
```

Important consequences:

- suppression is per `ApplicationErrorReporter` instance/process;
- it resets on process restart;
- it does not survive as persisted dedup state;
- it is based on fingerprint, not `error_id`/`correlation_id`;
- a suppressed event-log duplicate can still have been written to the rotating log.

## 10. Event-log persistence failure

`ApplicationErrorReporter` is deliberately best-effort.

If appending to `event_log` fails:

- the original application workflow is not failed solely because reporting failed;
- the reporter emits a debug log attempt about the reporting failure;
- the caller still receives/retains the reported error/correlation identity generated before persistence.

Therefore presence of an `err_*`/`corr_*` shown to the user does not mathematically prove that a corresponding SQLite event row exists.

## 11. Event-log ordering and limits

`SQLiteEventLogRepository.list_recent(limit)` clamps the requested limit to:

```text
1 <= limit <= 500
```

Rows are ordered by:

```text
occurred_at DESC,
id DESC
```

The timestamp is stored as text and current reporter events use UTC ISO strings. The database does not enforce a timestamp format with an SQL constraint.

## 12. Runtime-operation evidence

Runtime operations are persisted separately in:

```text
runtime_operations
runtime_operation_resources
```

Their state/claim contract is described in:

- `architecture/runtime-resource-safety.md`;
- `reference/persistence-schema.md`;
- `reference/statuses-and-identifiers.md`.

Operations Center combines those persistent operations with event-log records for presentation, but does not merge them into one storage schema.

## 13. Operations Center item projection

`OperationsCenterItem` is a presentation projection containing:

```text
item_id
title
summary
status
severity
occurred_at
target_screen
focus_text
correlation_id
operation_kind
operation_state
operation_subject
operation_error
focus_key
error_id
user_message
```

It is derived state. It is not another persistence store.

### 13.1 Runtime-operation item IDs

```text
operation:<operation_id>
```

### 13.2 Event item IDs

```text
event:<event_id>
```

These prefixes belong to Operations Center item identity, not to the underlying domain ID generators.

## 14. Operations Center active items

`active_items()` reads `list_active_operations()` and maps each runtime operation into one item.

If the runtime-operation read raises, current behavior returns an empty tuple rather than propagating the read failure through this method.

Active-operation severity projection:

```text
failed / abandoned      -> error
cancelling / cancelled  -> warning
starting / running      -> active
other terminal state    -> success
```

## 15. Recent activity

`recent_activity(limit=24)` combines:

1. recent runtime operations;
2. recent event-log records except event types beginning with `automation.run.`.

Both reads are individually best-effort; failure of one source yields no items from that source while the other source can still contribute.

Projection then:

```text
collect operation items + event items
        ↓
deduplicate by OperationsCenterItem.item_id
        ↓
sort occurred_at descending
        ↓
take max(1, limit)
```

Excluding `automation.run.*` here prevents those Automation audit events from being duplicated into the generic recent-activity stream in the current UI model. It does not delete them from the event log.

## 16. Issue items

`issue_items(limit=24)` reads a wider recent event window:

```text
max(limit * 4, 40)
```

and keeps only:

```text
event_type in {application.error, application.notice}
AND
severity in {warning, error, critical}
```

Then it returns the first `max(1, limit)` projected items in the event-log order.

This means the Issues view is a filtered presentation of recent reporter events, not a complete historical incident database.

## 17. Event severity projection

For Operations Center:

```text
application.error -> error
```

regardless of payload level.

For other reporter events, payload `level` is case-folded:

```text
critical / fatal -> critical
error            -> error
warning          -> warning
anything else    -> info
```

Malformed/non-object `payload_json` is tolerated as `{}` by projection helpers.

## 18. Semantic user messages

When reporter payload contains:

```json
{
  "user_message": {
    "key": "...",
    "values": {...}
  }
}
```

Operations Center reconstructs a `UserMessage` if the key is valid.

This preserves the architectural separation:

```text
persisted semantic message identity
        ↓
UI localization boundary
        ↓
localized visible text
```

A historical payload without `user_message` can still be displayed from its diagnostic summary; it simply lacks this semantic-localization path.

## 19. Target-screen routing

Runtime operations use explicit operation-kind routing:

```text
training             -> Training
personality_test     -> Tests
analysis             -> Analysis
inference            -> Training / model check
lineage_delete       -> Agents / delete branch
automation_recipe    -> Automation
automation_command   -> Automation
unknown              -> Dashboard
```

Event rows use heuristic routing over `component + entity_kind + entity_id` text. Recognized concepts currently route to Training, Tests, Analysis, Automation, Datasets, Snapshots, Agents or Key Bindings; unmatched events route to Dashboard.

### Boundary

Event target routing is a convenience heuristic. It is not durable semantic evidence about the event's true owning subsystem.

## 20. Correlation and causation

The event schema supports both:

```text
correlation_id
causation_id
```

Current `ApplicationErrorReporter` populates `correlation_id` but writes `causation_id = NULL` for its own events.

Therefore the existence of a causation column must not be documented as a fully populated distributed causal trace. Correlation is the actively used reporter identity today.

## 21. What diagnostic evidence can and cannot prove

A stored event can prove that PTL persisted a particular diagnostic payload at a particular recorded time.

It does not by itself prove:

- that every occurrence of a repeated error was persisted;
- that every diagnostic string is secret-free;
- that a user-visible `err_*` necessarily reached SQLite;
- that `occurred_at` is cryptographically trustworthy time;
- that event ordering reconstructs every concurrent causal edge;
- that heuristic target-screen routing identifies true ownership;
- that a fingerprint uniquely identifies one root cause;
- that `causation_id` is populated for reporter events.

## 22. Operator evidence bundle

When preserving an incident for diagnosis, prefer keeping together:

```text
app.db
logs/persona_training_lab.log*
relevant workspace files/artifacts
reported err_* / corr_* identity
current source commit / release identity
```

Do not reset/delete workspace state before collecting evidence when the failure is not yet understood.

## 23. Change checklist

Any change to reporter/event/Operations Center semantics should trigger review of:

1. `application/errors/reporter.py` tests;
2. event-log repository/schema tests;
3. Operations Center service tests;
4. `reference/persistence-schema.md` when SQL fields/indexes change;
5. `reference/statuses-and-identifiers.md` when event/ID families change;
6. `operations/troubleshooting.md` for operator-facing diagnosis;
7. `operations/security-boundaries.md` for privacy/redaction changes;
8. `architecture/ui-shell.md` when Operations Center routing/ownership changes;
9. localization catalogs when semantic user-message keys change;
10. release-gate/visual evidence if Issues/Activity behavior changes visibly.
